# Аудит проекта «Хиромант»

Дата проверки: 6 сентября 2026 года  
Источник: `minimalist-palmistry-app-concept.zip`

## Резюме

«Хиромант» — клиентский MVP на React 19 + Vite 7 + TypeScript + Tailwind CSS 4. Приложение реализует последовательный сценарий: имя → снимок ладони → выбор руки → калибровка линий → персонализированное чтение → экспорт результата в PNG/SVG.

**Для Render Static Site проект подходит:** backend не используется, сетевых запросов и внешних API нет, фотографии обрабатываются в памяти браузера через `canvas`. Production-сборка успешна.

| Область | Статус | Комментарий |
|---|---:|---|
| Сборка | Готово | `npm run build` проходит; Vite формирует единый `dist/index.html` |
| Типизация | Готово | `npx tsc --noEmit` проходит без ошибок |
| Static deployment | Готово | Подходит Render Static Site или GitHub Pages |
| Камера | Требует проверки | Нужен HTTPS и разрешение пользователя; предусмотрен fallback на upload |
| Анализ фото | MVP/эвристика | Skin-mask + Sobel + шаблонные анатомические линии, не computer vision-модель |
| Доступность | Требует доработки | Не хватает явных focus-состояний, aria-атрибутов и клавиатурной проверки |
| Продуктовый риск | Важно | Нужно явно отделить развлекательную хиромантию от медицинских/фактических обещаний |

## Как устроен проект

Входная точка — `src/main.tsx`, основной state machine — `src/App.tsx`. Состояние сценария хранится только в React state, поэтому перезагрузка страницы сбрасывает сессию.

Основные модули:

- `Capture.tsx` — камера, загрузка файла, квадратный crop, JPEG data URL.
- `HandSelection.tsx` — выбор левой/правой руки.
- `AdjustLines.tsx` — overlay изображения, SVG-линии и drag-точки.
- `autoDetectLines.ts` — локальная эвристическая обработка изображения.
- `palmistryRules.ts` — детерминированный генератор текстового результата по геометрии линий.
- `Reading.tsx` и `HandArtwork.tsx` — экран результата и экспорт PNG/SVG.

Сторонние изображения и шрифты не используются: это хорошо для автономного статического деплоя и конфиденциальности.

## Что уже сделано хорошо

1. **Простой и понятный сценарий.** Пользователь последовательно проходит пять шагов, а состояние не размазано по роутеру или глобальному store.
2. **Локальная приватность.** В текущем коде нет `fetch`, backend или загрузки фото на сервер. Фото остаётся в data URL и памяти вкладки.
3. **Хорошая визуальная идея.** Минималистичная чёрно-белая база, тонкие границы, цветовой код линий и отдельная тёмная карточка «карты судьбы» создают узнаваемый стиль.
4. **Есть graceful fallback.** Если camera API недоступен или авторазметка не удалась, пользователь может загрузить фото и/или выставить линии вручную.
5. **Экспорт без сервера.** SVG создаётся как Blob, PNG — через canvas; это естественный функционал для статического сайта.
6. **Production-сборка уже оптимизирована под один HTML-файл.** `vite-plugin-singlefile` встраивает CSS и JS в `dist/index.html`, что упрощает доставку.

## Найденные проблемы и приоритеты

### P0 — исправить до публичного запуска

#### 1. Нельзя обещать точное распознавание линий

`autoDetectLines.ts` действительно анализирует цвет кожи и границы Sobel, но затем создаёт четыре линии из анатомического шаблона (`buildAnatomicalLines`) и слегка сдвигает только control points к самым сильным границам. Это не надёжное распознавание складок ладони. На сложном фоне, при плохом освещении, другой ориентации или частично обрезанной ладони результат может быть убедительным визуально, но неверным.

**Рекомендация:** на UI называть функцию «черновая авторазметка» или «предварительная разметка», всегда оставлять ручную корректировку и показывать короткое пояснение: «Алгоритм предлагает точки, финальная точность зависит от вашей корректировки».

#### 2. Убрать медицинские и причинно-следственные формулировки

В правилах встречаются формулировки про здоровье, долголетие, жизненный потенциал и «здоровье». Для развлекательного продукта безопаснее прямо указать, что это интерпретация/рефлексия, а не диагностика, прогноз здоровья или научный вывод.

**Рекомендация:** добавить дисклеймер на welcome и перед результатом: «Для развлечения и саморефлексии. Хиромантия не является научным методом и не заменяет медицинские, финансовые или психологические рекомендации». В `PalmGuide` заменить категоричные формулировки на «в традиции трактуется как…».

### P1 — желательно сделать до первого маркетингового трафика

#### 3. Не хватает обработки файлов

Сейчас принимается любой `image/*`, файл полностью читается в data URL, размер не ограничивается. Очень большая фотография может занимать много памяти; повреждённый файл может тихо остаться без понятной ошибки.

**Рекомендации:**

- ограничить размер, например 10 MB;
- проверять `file.type` и показывать понятную ошибку;
- передавать image через `HTMLImageElement`, затем ресайзить до разумного максимума (например, 1600 px) перед сохранением;
- сбрасывать value у input, чтобы повторная загрузка того же файла снова вызывала `onChange`.

#### 4. Камера требует явного поведения при unmount и смене режима

Текущая логика в целом корректна, но стоит добавить `playsInline`, уже присутствующий, и явную кнопку остановки/возврата из camera preview. На некоторых мобильных браузерах нужно также обработать случай, когда `videoWidth === 0` и пользователь нажал снимок слишком рано.

#### 5. Drag-точки работают, но взаимодействие можно сделать устойчивее

Сейчас движение отслеживается на SVG (`onMouseMove`/`onTouchMove`), а отпускание — глобально. На мобильном устройстве при быстром движении палец может выйти за SVG; перемещение прекратится до следующего события. Лучше перейти на Pointer Events (`onPointerDown`, `setPointerCapture`, `onPointerMove`, `onPointerUp`). Также стоит добавить `aria-label` к точкам и клавиатурный способ корректировки.

#### 6. Страница не имеет metadata для шаринга и локали

`index.html` имеет `lang="en"`, хотя интерфейс русский. Нет description, theme-color, Open Graph и favicon.

Минимум:

```html
<html lang="ru">
<meta name="description" content="Хиромант — развлекательное чтение линий ладони прямо в браузере.">
<meta name="theme-color" content="#fdfdfb">
```

### P2 — улучшение качества

#### 7. Accessibility

Рекомендуется добавить видимые `:focus-visible` состояния, `aria-pressed` для выбора руки и вкладок/аккордеона, `aria-live="polite"` для статусов «Сканирую ладонь…», label для всех icon-only кнопок, а для модального окна — `role="dialog"`, `aria-modal="true"`, возврат фокуса и закрытие по Escape.

#### 8. Стабильный ID результата

В `HandArtwork.tsx` ID генерируется через `Math.random()` во время каждого render. При любом изменении состояния карточки ID может измениться. Это не критичная ошибка, но для UX лучше создать ID один раз через `useState`/`useRef` и использовать криптографически более качественный `crypto.randomUUID()` с fallback.

#### 9. Удалить неиспользуемый ref и проверить формат имени файла

`artworkRef` сейчас не используется. Имя пользователя попадает только в атрибут `download`, что безопасно для DOM, но для удобства экспорта лучше нормализовать имя файла: убрать slash, двоеточия и управляющие символы.

#### 10. Визуальная проверка на маленьких экранах

Сценарий в основном адаптивный, но экран калибровки содержит квадрат 288/400 px плюс длинный контент и footer. На коротких мобильных экранах часть controls будет ниже fold. Стоит проверить iPhone SE/Android 360 px и добавить прогресс-бар с текущим шагом вместо только label в header.

## Деплой на Render Static Site

### Вариант A: Render подключён к GitHub

1. Создать репозиторий и загрузить содержимое проекта, **не загружая `node_modules` и `dist`**.
2. В Render выбрать **New → Static Site**.
3. Подключить нужный GitHub repository и ветку, обычно `main`.
4. Указать настройки:

| Поле Render | Значение |
|---|---|
| Build Command | `npm ci && npm run build` |
| Publish Directory | `dist` |
| Auto-Deploy | `Yes`, если нужен деплой после push |
|

5. После первого деплоя открыть выданный `onrender.com` URL и проверить камеру. Камера работает только в secure context: Render URL по HTTPS подходит.

Для Vite в данном проекте `base` по умолчанию `/` корректен для Render Static Site на отдельном домене.

### Вариант B: собирать в GitHub Actions и публиковать готовый dist

Для Render это не требуется: проще и надёжнее дать Render выполнить `npm ci && npm run build` из репозитория. Если всё же коммитить `dist`, нужно согласовать стратегию с командой, иначе `dist` может устаревать относительно `src`.

## Приоритетный план следующего шага

1. Добавить `.gitignore`, README с Render-настройками и metadata `lang="ru"`.
2. Добавить дисклеймер и смягчить медицинские/фактические обещания.
3. Ограничить размер изображения и добавить валидацию ошибок.
4. Перевести drag interaction на Pointer Events и добавить accessibility.
5. Протестировать на HTTPS Render с реальным мобильным Safari/Chrome: камера, повторная загрузка, поворот экрана, отказ в разрешении, плохое фото и экспорт PNG.
6. После этого запускать небольшой UX-тест на 5–10 людях: где они сомневаются, понимают ли разницу между авторазметкой и анализом, находят ли кнопку ручной корректировки.

## Итоговая оценка

**Техническая готовность к статическому деплою: 8/10.**  
**Готовность к публичному продукту: 6/10.**

Сильная сторона проекта — цельный визуальный MVP, который уже можно открыть на Render без backend. Главная зона роста — честно позиционировать автоанализ как развлекательную эвристику, укрепить мобильное взаимодействие с линиями и закрыть базовые accessibility/privacy-доверительные детали.
